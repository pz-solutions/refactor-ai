### R1 — Restrict helper discovery to the installed toolkit

Location: `src/backends/csharp.ts:152–179`, with the current-directory candidate at `:189`.

`findOrBuildHelper()` searches every candidate root for a compiled helper before considering any helper sources. npm and skill packages initially contain sources, not compiled DLLs. If the target working directory contains `dotnet/RefactorHelper/bin/Release/net8.0/RefactorHelper.dll`, that DLL wins over building the helper in the explicitly configured `REFACTOR_AI_HOME`.

**Verified with the real .NET runtime:** compiled a separate executable named `RefactorHelper`, copied its output into that path in a temporary target repository, and invoked the generated npm CLI's C# `plan format`. The foreign executable wrote a marker outside the target root and returned a valid-looking response. The CLI reported `validation.status: passed`. The installed npm package contained its own helper sources throughout the experiment. No PATH substitution was used for this verification.

This permits execution with the CLI user's permissions before the intended compiler engine loads the project. A harmless stale helper in that location also invalidates the claim that the packaged engine determines the transformation.

**Fix:** when a package or skill supplies `REFACTOR_AI_HOME`, make that root authoritative and build/load only its helper. For checkout use, infer the toolkit root from the entry module; avoid treating the analyzed repository's cwd as an executable search location. Fail explicitly when the selected toolkit is incomplete.

**Regression:** use a fresh installed package with no compiled helper and a target cwd containing a foreign helper. Assert that the foreign marker is absent and that the packaged helper is built and used. Test the same case through an installed skill.

### R2 — Preserve global usings when deleting a moved type's source

Location: `dotnet/RefactorHelper/FileOperations.cs:169`, `:230`, and `:242–243`.

The source-deletion condition checks the number of types and assembly attributes, but does not check global usings. The created compilation unit deliberately excludes global usings. Consequently, moving the only type deletes the source's project-wide imports.

The semantic verification does not catch every resulting change: `TypeRelocation.Mentions()` limits candidates to documents mentioning the moved type, its extension methods, or a plain using of its old namespace. An unrelated document relying on a removed global static using can bind to another valid overload and remain outside that set.

**Verified:** a restored .NET 8 executable with these files:

```csharp
// Payload.cs
global using static N.Tools;
namespace Demo;
public class Payload {}

// Consumer.cs
global using static N.OtherTools;
namespace Demo;
class Program { static void Main() { System.Console.WriteLine(Pick(1)); } }

// Tools.cs
namespace N {
    public static class Tools { public static int Pick(int x) => 1; }
    public static class OtherTools { public static int Pick(object x) => 2; }
}
```

Moved `Payload` into `Moved.cs` in the same project and namespace. Both plan and apply succeeded, with zero new diagnostics. `dotnet run` printed `1` before and `2` afterward.

**Fix:** keep a source file that still contains global directives, or preserve those directives in their original project through an explicit planned file change. A cross-project move must leave source-project global imports in the source project. Do not copy them into the destination project indiscriminately.

**Regression:** cover global namespace imports, aliases, and static imports, including an overload-resolution case that compiles both before and after. Include same-project and cross-project moves.

### R3 — Persist new project references in an unconditional context

Location: `dotnet/RefactorHelper/ProjectFiles.cs:360–372`; item insertion at `:108–117`.

`AddProjectReference()` selects the last XML ProjectReference regardless of its containing group's condition. `InsertItem()` puts the new item directly after that element, inside the same group. Meanwhile, the in-memory Roslyn solution adds the reference unconditionally. Those two representations can describe different project graphs.

**Verified:** three restored .NET 8 solution projects, A/B/C. Project A initially contained:

```xml
<ItemGroup Condition="'$(Configuration)' == 'Release'">
  <ProjectReference Include="../C/C.csproj" />
</ItemGroup>
```

A declared `Demo.Payload` and a separate consumer of that type. B had no dependency on A. Moving Payload from A to B required A → B. The plan passed and inserted:

```xml
<ItemGroup Condition="'$(Configuration)' == 'Release'">
  <ProjectReference Include="../C/C.csproj" />
  <ProjectReference Include="../B/B.csproj" />
</ItemGroup>
```

After apply, the default Debug solution build failed with `CS0246` in A's consumer. The in-memory validation had reported no new errors.

The early existing-reference check also accepts an XML reference without considering whether its condition makes it active, creating another route to the same mismatch.

**Fix:** use an unconditional ItemGroup for unconditional new references, or reject conditional/unknown reference rules. Establish that an existing XML reference applies to the evaluated configuration before skipping a required edit. Validate persisted project graph semantics against the in-memory graph.

**Regression:** add inactive conditional groups, conditioned individual references, and Debug/Release builds of the applied result. Verify that a successful plan results in a compiling persisted project.

### R4 — Handle initialization effects before moving TS/JS runtime classes

Location: `src/backends/typescript-fileops.ts:551–560`, with reference-count checks at `:598–601`.

The backend applies TypeScript's Move to file action and checks references, membership, project dependency cycles, and compiler diagnostics. It does not check module-level initialization effects. Reference preservation does not preserve when a runtime class initializes.

**Verified:** strict TypeScript compiled to CommonJS with target ES2022:

```typescript
// types.ts
export function mark(value: string) { console.log(value); return value; }
export class First { static value = mark("first"); }
export class Payload { static value = mark("payload"); }
export class Last { static value = mark("last"); }

// main.ts
import { First, Payload, Last } from "./types";
console.log(First.value, Payload.value, Last.value);
```

Moving Payload into `Payload.ts` returned a passed plan with no notes. Both versions compiled. Initialization output changed from `first, payload, last` to `first, last, payload`; the final values were unchanged. Initialization order can matter for registration, callbacks, and shared state.

Import sorting already documents this risk, but move-type does not. Deterministic edits should not be presented as proof of behavior preservation for this accepted case.

**Fix:** conservatively reject moves involving effectful static initializers, static blocks, decorators, or other module-evaluation dependencies until a supported policy exists. If such moves are intentionally supported, make the limitation visible in operation help and the individual plan, and require an explicit choice for the risky case. Pure type-only declarations can remain a safer initial scope.

**Regression:** compare emitted program output for this fixture; cover both TS and JS, static blocks, decorators, and module cycles within a single project.

### R5 — Carry and restore file permissions explicitly

Location: `src/core/apply.ts:30–41` and `:121–125`.

The staging file is opened with the original mode, but file creation applies the process umask to that mode. No subsequent chmod restores the exact permissions. Creations representing a file rename use the default 0666 creation mode and have no link to the deleted source's metadata.

**Verified under umask 022:**

- A JS symbol rename changed an existing file from mode 0664 to 0644.
- TS rename-file changed `Wrong.ts` at mode 0600 into `Widget.ts` at mode 0644. Access was broadened to other users despite the operation only intending a name change.

The current rollback test uses 0751, whose bits are unaffected by umask 022, so it does not catch the edit/rollback issue.

**Fix:** after creating a staging file, apply the exact preserved mode before replacement. Extend plan/journal metadata so a pure file rename preserves its source permissions and recovery can restore them. Define an explicit conservative policy for split-type file creation.

**Regression:** test 0664 and 0770 under umask 022, 0600 pure renames, executable JS renames, and permissions after rollback. Keep platform-specific expectations explicit.

### R6 — Normalize Windows paths throughout TS/JS handling

Location: `src/backends/typescript.ts:68–70`. Further slash-specific logic appears in `typescript-vfs.ts`, `typescript-fileops.ts`, and `typescript-workspace.ts`.

The basic backend identifies a config filename using `project.slice(project.lastIndexOf("/") + 1)`. Node's ordinary absolute Windows path `C:\repo\tsconfig.json` contains backslashes, so that expression returns the whole path and rejects it with `UNSUPPORTED_PROJECT`. CLI inputs are canonicalized, so supplying a forward-slash spelling is not a reliable workaround.

**Verified at the pathname-expression level:** the actual expression rejects that Windows path; `path.win32.basename()` correctly returns `tsconfig.json`. This affects rename, imports, format, and both extraction operations. An end-to-end Windows run was not performed on this macOS host.

The file-operation VFS also splits filesystem paths on `/` and builds glob expressions around `/`, while module specifiers are constructed from platform-specific `path.relative()` results. Fixing the basename check alone does not establish Windows support for the entire toolkit.

**Fix:** use path utilities for filesystem paths and a defined normalized representation inside the TS VFS; convert generated module specifiers to forward slashes. Add Windows CI for actual installed npm packages and copied skills. Until then, explicitly scope supported runtime platforms.

**Regression:** execute plan/preview/validate/apply on Windows for all operations, including explicit files lists, nested move destinations, and generated imports. Retain POSIX tests.

## Other reviewed properties and remaining limits

- Skills use English instructions and direct the agent to operation-specific help; installed launchers and npm tools run built JavaScript through Node. First-use dependency and SDK requirements are documented.
- The plan/apply workflow checks content freshness, creation/deletion preconditions, root boundaries, and plan structure. Those checks are useful, but stored compiler diagnostics are not recompiled by validate/apply, and an unkeyed plan hash is not authentication. Treat externally supplied plans as executable change instructions requiring review.
- Compiler dependencies outside the root, dynamic references, reflection, assembly identity changes, and lack of automatic recovery are documented limitations. They are not additional undisclosed findings in this report.
- Packaging has pinned dependencies, dependency lockfiles for skills/helper builds, allowlisted publication files, and no installation lifecycle scripts. Integration tests exercise actual archives and independent skill copies.
- Workflow review found pinned action revisions, read-only verification permissions, a separate tag-gated publishing job, same-run artifact consumption, publication preflight, and a default dry-run manual path. No real GitHub run or authenticated npm publication was performed, so live account/OIDC configuration is not validated here.
- Existing tests heavily exercise supported happy paths and rejected structural conflicts. The missing tests above concern changes that still compile, persisted MSBuild evaluation, initial helper lookup, metadata, and a second runtime platform. Add these regressions before expanding the operation catalog.

Suggested order: R1 first, then R2/R3, then the runtime-move policy in R4. Resolve R5/R6 before claiming preservation of file metadata or broad platform portability. Rebuild all generated skill and npm resources after implementation fixes.
